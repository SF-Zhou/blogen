# Verification harness (`scripts/verify/`)

Dev-only parity gate for `blogen`. Nothing here is part of the crate; no Node
dependency is needed to **build** blogen, only to run this harness.

The harness answers one question: *does blogen's generated site match the site
the original generator produces from the same posts?*

```
                   git archive HEAD (read-only)
  blog checkout ───────────────────────────────► make_baseline.sh ──► .cache/baseline/
  (Node generator)                                                     public/ profile/ manifest.json
                                                                              │
  blogen build (candidate site dir) ─────────────────────────────► compare_sites.py  ──► PASS / FAIL report
                                                                              │
                                                    screenshots.mjs ──────────┴──► .cache/screenshots/ (PNGs + report.json)
```

The real blog checkout (`../blog`) is **never** built in place. All Node builds
happen in throwaway `git archive <legacy-ref>` copies; the legacy `node_modules`
directory is reused read-only (or re-installed from the frozen dependency set).

## Migration status — one-time gate

This harness was the **one-time migration gate** for replacing the legacy blog
generator with blogen. The blog repository has since been migrated: its
`build.sh` now calls `blogen build`, and the legacy `src/*.js`, `config.json`,
`package.json`, `dist/` and npm dependencies were removed from the working tree.
Therefore:

* the harness is **not needed for the blog's CI anymore** — it is kept for
  auditing/reproducing the migration result and for future parity checks;
* the Node baseline is **pinned to the last legacy-generator commit**
  (`d4cb7aafad90f09cdcd85e2482eae739483743a5`, recorded in
  `.cache/baseline/manifest.json`); after the migration commit, HEAD no longer
  contains the legacy generator, so `make_baseline.sh` automatically falls back
  to that pinned ref (see "Baseline after the blog migration");
* the frozen legacy dependency set is committed as `legacy-deps.json` +
  `legacy-package-lock.json`, so the baseline can be regenerated byte-identically
  even though the blog's `node_modules` was deleted (verified:
  `public_sha256 = c57bc1d3…`).

## Requirements

| tool | why |
| --- | --- |
| `python3` (3.8+) + `PIL`/`numpy` | `compare_sites.py` (stdlib only) and `pixdiff.py` (PIL+numpy for pixel diffs) |
| Node 24 (`source ~/.nvm/nvm.sh && nvm use 24`) | baseline build (`./build.sh`), fixture oracle, puppeteer screenshots |
| blog checkout at `../blog` (full git history) | `git archive` of the pinned legacy generator commit |
| legacy Node dependency tree | baseline rebuilds only: a preserved `node_modules`, or bootstrap once with `make_baseline.sh --bootstrap-node-modules` (frozen lock, ~500 MB in `.cache/legacy-deps/node_modules`) |
| puppeteer + Chrome | chrome already installed in `~/.cache/puppeteer`; the puppeteer package is loaded from `blog/node_modules` or, post-migration, from the frozen `.cache/legacy-deps/node_modules` (bootstrap) |

`scripts/verify/.cache/` is git-ignored and can be deleted at any time. No
`node_modules` is created inside the blogen repo.

## Quick start (migration gate command)

```bash
# Gate used for the migration, against a blogen-generated site:
python3 scripts/verify/compare_sites.py --candidate <candidate>     # report + exit code
scripts/verify/run.sh --candidate <candidate>                       # everything (+ self-test)
scripts/verify/run.sh --candidate <candidate> --screenshots         # + pixel diff
```

A candidate is any blogen output dir (site root, or build dir containing
`public/`). See below for building one from the real blog.

## Quick start

```bash
# 1. Build the Node baseline (~5 s). Re-run any time; it is idempotent.
scripts/verify/make_baseline.sh

# 2. Sanity-check the comparer itself (no sites needed).
python3 scripts/verify/compare_sites.py --self-test

# 3. Build a blogen candidate site and compare it with the baseline.
#    <candidate> is either the site root (contains index.html) or a build dir
#    containing public/index.html (+ profile/README.md next to it).
python3 scripts/verify/compare_sites.py --candidate <candidate>

# 4. Or run everything through the orchestrator:
scripts/verify/run.sh --candidate <candidate>
scripts/verify/run.sh --candidate <candidate> --screenshots
scripts/verify/run.sh --rebuild-baseline --candidate <candidate> --fixtures-check
scripts/verify/run.sh                       # baseline build + self-test only

# 5. Screenshots alone: baseline-only capture (works before blogen can build),
#    or baseline vs candidate pixel diff.
node scripts/verify/screenshots.mjs
node scripts/verify/screenshots.mjs --candidate <candidate>

# 6. Regenerate / verify the Rust integration-test fixtures.
scripts/verify/make_fixtures.sh
scripts/verify/make_fixtures.sh --check
```

`run.sh` exit codes: `0` pass, `1` parity/visual mismatch or stale fixtures,
`2` usage/infrastructure error.

## Baseline after the blog migration

`make_baseline.sh` resolves the legacy generator commit in this order:

1. `--ref REF` / `$BLOGEN_BASELINE_REF` (must contain `src/main.js`);
2. `HEAD`, when HEAD still has the legacy generator;
3. the pinned legacy commit `d4cb7aafad90f09cdcd85e2482eae739483743a5`.

If none of these exists it exits with a clear message (set
`BLOGEN_BASELINE_REF` to an older legacy commit or fetch the full blog history).
The manifest records `source.ref`, `source.ref_source`, `source.commit` and
`source.head_commit`, so the provenance stays clear after the switch.

The legacy Node dependency tree is resolved as `--node-modules` /
`$BLOGEN_BASELINE_NODE_MODULES`, else `<blog>/node_modules`, else
`.cache/legacy-deps/node_modules`. After the migration deleted `blog/node_modules`,
bootstrap it once (network needed, ~500 MB, frozen versions from
`legacy-deps.json`/`legacy-package-lock.json`):

```bash
scripts/verify/make_baseline.sh --bootstrap-node-modules
# or, if you have a preserved copy:
BLOGEN_BASELINE_NODE_MODULES=/path/to/legacy/node_modules scripts/verify/make_baseline.sh
```

A previously built `.cache/baseline/` keeps working without any of this;
`run.sh` only rebuilds the baseline when it is missing or `--rebuild-baseline`
is passed. The fixture oracle (`make_fixtures.sh`) uses the same ref and
node_modules resolution rules.

Post-migration audit: build the migrated blog (which now uses blogen) from an
archive of its current HEAD and compare with the pinned baseline:

```bash
tmp=$(mktemp -d)
git -C ../blog archive HEAD | tar -x -C "$tmp"
( cd "$tmp" && ./build.sh )              # build.sh now runs `blogen build`
scripts/verify/run.sh --candidate "$tmp" --screenshots
```

## Building a candidate for the real blog (pre-migration)`

`blog-site.toml` maps the old `blog/config.json` onto blogen's TOML schema. The
blog checkout stays read-only; build in a temp directory with a symlinked
`posts/` tree:

```bash
BLOG=$(cd "$(dirname scripts/verify/README.md)/../.." && pwd)/../blog
tmp=$(mktemp -d)
ln -s "$BLOG/posts" "$tmp/posts"
cp scripts/verify/blog-site.toml "$tmp/blogen.toml"
cargo run -q -- --config "$tmp/blogen.toml" build     # --config is a global flag
scripts/verify/run.sh --candidate "$tmp" --screenshots
```

`$tmp` then contains `public/` (the site root) and `profile/README.md`. Note:
the blog posts only reference local images; if remote images ever appear, use a
copy of `posts/` instead of a symlink so the blog checkout is not mutated.

## Candidate site layout

`compare_sites.py` and `screenshots.mjs` accept either:

```
<candidate>/index.html              # site root
<candidate>/profile/README.md       # optional profile output (sibling)
```
or
```
<candidate>/public/index.html       # e.g. a build dir with output_path = public
<candidate>/profile/README.md
```

Override the profile location with
`compare_sites.py --candidate-profile <file>`. The candidate must contain
`index.html`, `index.json`, `rss.xml` and the article pages
(`article.html` / hidden `article.htm`); theme assets under `dist/` are
compared only through references/broken-link checking (the CSS/JS is owned by
the theme agent and is not byte-comparable with the old lessc output).

## Files

| file | purpose |
| --- | --- |
| `make_baseline.sh` | Node oracle build (`git archive HEAD` -> `./build.sh` -> `.cache/baseline/`), writes `manifest.json` with commit/node/dep versions and tree hashes |
| `compare_sites.py` | the gate: per-article body classification, metadata, index.json/index.html/rss/profile, inventory, local links; `--self-test` has built-in comparer checks |
| `make_fixtures.sh` / `make_fixtures.py` | regenerate `tests/fixtures/expected/` with the original Node pipeline (`--check` for staleness) |
| `screenshots.mjs` | puppeteer capture (1100×900 full page, light+dark) + pixel diff; can run baseline-only |
| `pixdiff.py` | PNG pixel diff (PIL+numpy), writes diff images |
| `check_static_mermaid.mjs` | verifies Mermaid figures are static/JS-free: inline light+dark SVG, no mermaid scripts/assets, and pixel-identical rendering with `setJavaScriptEnabled(false)` |
| `make_parity_images.mjs` / `make_parity_images.py` | capture + compose the evidence images in `docs/parity/` (kept <600 KiB) |
| `run.sh` | orchestrator: self-test -> baseline -> fixtures -> compare -> screenshots |

Outputs:

* `.cache/baseline/` — Node baseline: `public/`, `profile/README.md`,
  `config.json`, `build.log`, `manifest.json`.
* `.cache/screenshots/<label>/*.png` — screenshots, `.cache/screenshots/diff/*.png`
  — diff images, `.cache/screenshots/report.json` — diff report.
* `.cache/reports/compare-latest.json` — last comparer report (JSON); override
  with `--report FILE`.

## What `compare_sites.py` checks

1. **Article inventory** — every baseline article page (`.html` visible, `.htm`
   hidden) must exist in the candidate and vice versa. Missing/extra article
   pages are hard failures.
2. **Per-article body HTML** — the inner HTML of `<div class="markdown">` is
   extracted from each article page and classified:
   * `identical` — byte-for-byte equal;
   * `equivalent` — equal after the allowed normalisations below (pass);
   * `different` — hard failure with a readable unified diff of the first
     differing lines.
3. **Article page metadata** — `<title>`, `h1`, date, author text, author link
   must match exactly.
4. **`index.json`** — same article set and fields (`title`, `date`, `author`,
   `author_url`, `tags`, `filename`, `url_path`; tag order significant). Article
   ordering differences are `equivalent` (the old JS comparator was unstable on
   date ties; blogen sorts date-desc, title-asc).
5. **`index.html`** — card list: title text, `url_path`, date, author, author
   link, tag text+href; same order/content, ordering difference is `equivalent`.
   Page `<title>`/`h1` must match.
6. **`rss.xml`** — channel fields (`title`, `link`, `description`, `language`,
   `atom:link` self link) and every item (`title`, `link`, `guid` +
   `isPermaLink`, `pubDate`, `dc:creator`, `category` list). `<lastBuildDate>`
   value is ignored (it is a build timestamp).
7. **`profile/README.md`** — exact; trailing-whitespace-only difference is
   `equivalent`.
8. **Inventory** — reports files the candidate did not regenerate and extra
   files (informational); image files that exist in both must have identical
   bytes (hard failure on mismatch).
9. **Local references** — every `href`/`src` in the candidate's generated HTML
   that points inside the site must resolve to an existing file/directory
   (broken local links are hard failures). This is the main gate on `dist/`
   assets without requiring byte-identical CSS/JS.

### Allowed differences (`equivalent`, never hard failures)

| difference | why it is acceptable | how it is normalised |
| --- | --- | --- |
| KaTeX internals (markup/classes/spacing changes between KaTeX versions) | version-dependent DOM, same rendered math | `<eq>`/`<eqn>` subtrees are compared by their original TeX from `<annotation encoding="application/x-tex">` (and the surrounding structure is compared) |
| Mermaid figure contents | baseline renders server-side SVG with mermaid-cli/puppeteer; blogen renders static inline SVG at build time with the pure-Rust `merman` renderer (small visual differences are accepted) | any element whose `class` contains `mermaid` is compared as an opaque placeholder; number and position of diagrams must match |
| attribute order, class token order, whitespace formatting, self-closing/boolean spelling | serializer differences | attributes sorted, class tokens sorted, insignificant whitespace collapsed/skipped |
| runs of whitespace in text nodes | HTML renders them identically | collapsed to one space |
| article ordering in index.json/index.html/rss | old comparator unstable on date ties, blogen is deterministic | sets compared; order difference reported as `equivalent` |
| RSS `<lastBuildDate>` | build timestamp | value ignored, presence still required |

Whitespace **inside `<pre>`/`<code>`** is significant and is compared exactly;
text/structure/math-content/heading-id/link/image changes are always hard
failures.

The comparer has unit-ish self-checks: `python3 scripts/verify/compare_sites.py
--self-test` (identical vs equivalent vs different cases for bodies, metadata,
index.json, RSS, profile, index cards).

## Screenshots (`screenshots.mjs`)

* Serves each site with `python3 -m http.server` on a free loopback port
  (absolute `/dist/...` asset paths work).
* External requests (giscus, Google Analytics) are aborted so captures are
  deterministic and offline.
* Puppeteer is loaded from `--blog-dir`/`../blog/node_modules`, falling back to
  `.cache/legacy-deps/node_modules` (frozen legacy deps) after the blog
  repository migrated and dropped its `node_modules`.
* Viewport 1100×900, full page height capped at `--max-height` (default 6000 px
  to bound memory), light and dark via `prefers-color-scheme`, animations
  disabled.
* Pages: `index.html` plus up to 7 representative pages auto-detected from the
  baseline HTML (mermaid, image figure, math, table, hidden `.htm`, nested dir).
  Override with `--pages a.html,b.html`.
* Pixel diff via `pixdiff.py` with a per-channel tolerance (`--tol`, default 12
  to ignore anti-aliasing/PNG noise); a page fails when more than
  `--threshold` percent (default 0.5%) of pixels differ. Mermaid pages are
  reported as **soft** (static `merman` SVG vs the baseline's server-rendered
  mermaid-cli SVG: an accepted visual difference) and never hard-fail, but their
  real pixel numbers are always captured. Every non-Mermaid comparison must
  stay at 0.000%.
* Mermaid figures are static inline SVG: captures never wait for client-side
  rendering. `check_static_mermaid.mjs` verifies the JS-free property (no
  mermaid scripts/assets, diagrams visible and pixel-identical with JavaScript
  disabled).
* Artifacts: `.cache/screenshots/baseline/<page>__<scheme>.png`,
  `.cache/screenshots/candidate/...`, `.cache/screenshots/diff/...` (diff
  highlighted in red), `.cache/screenshots/report.json`.
* Baseline-only mode (no `--candidate`) simply captures the baseline pages; it
  is the current mode until blogen can build the real blog.

## Fixtures for Rust integration tests

`tests/fixtures/` contains a small fixture site and the Node-generated oracle
for it, used by `tests/tests.rs`. See **`tests/fixtures/README.md`** for the
layout, oracle conventions (mermaid placeholder, `__LAST_BUILD_DATE__`, body
trim rule), feature coverage and regeneration instructions.

## Known accepted/reported differences

These are reported as warnings, not failures:

* RSS `<lastBuildDate>` differs (ignored).
* Article/card/RSS ordering differences (allowed, see above).
* Candidate-only or baseline-only non-article files (e.g. `.blogen-manifest.json`,
  changed theme asset file names) — reported for information; referenced assets
  must still resolve.
* Mermaid screenshot differences (soft): static `merman` SVG vs baseline
  mermaid-cli SVG (accepted visual difference; measured in `docs/parity/`).

Everything else — text, headings/anchors/TOC, code highlighting classes,
math TeX, images/figures, links, metadata, index/RSS/profile content, broken
local references — is a hard failure and must be fixed in blogen or the theme.
